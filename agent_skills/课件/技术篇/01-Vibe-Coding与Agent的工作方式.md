# 第 1 章：Vibe Coding 与 Agent 的工作方式

本章认识 Vibe Coding、Agent、模型和工具，通过一个IT 巡检待办网页观察“提出需求、生成文件、检查结果、继续修改”的过程。

我们以电商公司 IT 工程师的日常工作为背景：检查支付回调、订单状态与库存同步，整理故障资料并制作检查工具。先通过一个巡检待办网页理解 Agent 的工作过程。

## 1.1 什么是 Vibe Coding

假设你想制作一个IT 巡检待办网页，可以添加任务、标记完成和删除任务。现在，你可以先把想法告诉 AI，让它生成第一版，再根据实际效果继续提出修改要求。

这种以自然语言表达想法、让 AI 生成代码、通过查看和运行结果不断调整的开发方式，就是我们在课程中讨论的 Vibe Coding。

这个词在不同语境下有宽窄不同的用法。本课程以自然语言驱动应用开发为切入点，同时保留必要的结果检查。

### 工作方式发生了什么变化

人的注意力更多地放在“要解决什么问题”和“结果是否符合要求”上，AI 则承担大量代码生成与修改工作。

例如，你可以这样描述一个功能：

> 在每条任务旁边放一个完成按钮。点击后，任务文字加上删除线，并更新已完成数量。

AI 会把这个要求转成代码。随后，我们打开网页，点击按钮，观察效果，再决定是否继续修改。

### 不会编程，能不能使用

可以从简单页面、小工具和原型开始。但生成了代码，并不代表程序一定正确。随着需求变复杂，仍然需要逐步理解数据、运行环境和关键逻辑。

初学时先记住：**把需求说清楚，把结果运行起来，把关键功能检查一遍。**

## 1.2 什么是 Agent

Agent 通常译为“智能体”。在本课程中，可以把它理解为：**能够围绕目标，调用工具并连续推进任务的 AI 系统。**

你让 AI 制作网页，如果它只在聊天框中给出代码，保存文件、运行页面等工作还需要你完成。

具备相应工具和权限的 Agent，可以继续创建文件、修改代码、运行命令，并根据返回结果处理问题。它会在“判断下一步—调用工具—查看结果”的循环中推进任务。

```text
理解目标 → 决定下一步 → 调用工具 → 查看结果
              ↑                      ↓
              └──── 需要时继续调整 ────┘
                          ↓
                       交付成果
```

### 回答问题与执行任务

| 场景 | 提供回答 | 执行任务 |
| --- | --- | --- |
| 整理资料 | 告诉你整理方法 | 读取资料并生成整理结果 |
| 制作网页 | 提供代码或开发建议 | 创建文件并尝试运行 |
| 修改问题 | 分析可能的原因 | 修改相关文件并检查结果 |

有些聊天产品也具有工具调用能力，所以不能只看是不是聊天窗口。关键要看它能否操作实际材料、执行步骤并产生成果。

Agent 能完成到什么程度，取决于模型能力、可用工具、输入资料和权限。没有接入的服务，不会因为一句要求就自动变得可用。

## 1.3 模型、Agent 软件、工具和 Skills 的关系

学习这门课时，会听到 WorkBuddy、Codex、DeepSeek、Skills 等名字。它们分别负责不同的事情。

| 概念 | 负责什么 | 如何理解 |
| --- | --- | --- |
| 模型 | 理解输入、生成内容、提出下一步操作 | 处理信息与推理的核心组件 |
| Agent 软件 | 组织任务、连接模型、管理工具执行 | 我们实际使用的工作环境 |
| 工具 | 执行具体操作 | 读取文件、修改文件、运行命令等能力 |
| Skills | 提供可复用的工作方法与资源 | 告诉 Agent 某一类任务应该怎样完成 |

### WorkBuddy、Codex 与 DeepSeek

WorkBuddy 和 Codex 是本课程选择的两款 Agent 软件。我们会用 WorkBuddy 编写 Word 文档和 Excel 表格，用 Codex 编写、运行和修改 Python 程序。两款软件的能力存在交集，选择时根据任务、可用工具和工作环境判断。

DeepSeek 则是模型服务提供方。后续学习 Codex 时，可以选择 OpenAI 原生模型路线，也可以选择 DeepSeek 路线。客户端与底层模型是两个概念；DeepSeek 官方也提供了 Codex 接入说明。[DeepSeek 接入 Codex](https://api-docs.deepseek.com/quick_start/agent_integrations/codex/)

### 一次任务中，信息怎样流动

以“检查订单文件”为例，模型提出读取文件的操作，客户端调用文件工具；工具返回数据后，模型再决定运行程序或解释结果。文件读取、程序计算和模型回答分别发生在对应组件中。

如果数据保存在外部系统，可以用 MCP 连接该系统提供的工具；如果检查方法会重复使用，可以把步骤整理为 Skill。MCP 与 Skills 的具体用法将在后续章节展开。

### Skills 为什么值得单独学习

假设你每次整理资料，都要求 AI 按固定顺序工作：先阅读来源，再提取重点，接着区分事实与推测，最后按统一格式输出。

当这套方法被反复使用时，就可以将它整理成 Skill，减少每次重新交代流程的工作。技能可以包含说明、参考资料、模板，以及需要时使用的脚本。[Agent Skills 规范](https://agentskills.io/specification)

因此，课程会先教会大家使用软件，再重点介绍如何把自己的工作方法制作成 Skills。

## 1.4 怎样让 Agent 更准确地理解需求

自然语言可以降低操作门槛，但信息如果不够，AI 仍然需要猜测。

例如，“帮我做一个好用的管理系统”，没有说明管理什么，也没有说明具体功能。可以换成：

> 帮我做一个IT 巡检待办网页，支持添加任务、标记完成和删除任务。页面使用中文，样式简洁，在浏览器中打开即可使用。

这段话已经说明了要做什么、需要哪些功能，以及怎样使用。对于简单任务，这些信息就能帮助开始第一轮尝试。

### 三件事交代清楚

- **目标：** 想得到什么结果，例如一个IT 巡检待办网页。
- **材料和要求：** 有哪些资料，需要哪些功能，例如中文界面、添加和完成任务。
- **判断方法：** 怎样知道做对了，例如添加后能看到任务，标记完成后计数会变化。

如果任务需要参考某个文件，要把文件提供给 Agent，或明确指出位置。模型能利用的信息，就是它完成这次任务的上下文；文件放在电脑里，并不代表它已经读取。

复杂任务可以先让 Agent 说明准备怎么做，再逐步实现。第一版先完成主要用途，后面再增加新功能。

## 1.5 简单案例：制作一个IT 巡检待办网页

下面用一个连续案例展示工作过程。页面示意展示基本功能，实际生成的样式可能不同。

### 第一步：提出需求

向 Agent 输入：

```text
帮我制作一个中文IT 巡检待办网页。

要求：
1. 可以输入任务名称并添加到列表，空白内容不能添加。
2. 每条任务可以标记为完成，也可以删除。
3. 页面显示任务总数和已完成数量。
4. 初始放入三条未完成任务：检查支付回调、核对订单状态、检查库存同步。
5. 使用简洁的浅色界面，生成一个可在浏览器中直接打开的 index.html 文件。

第一版不需要登录，也不需要联网。任务暂时只保留在当前页面，刷新后恢复初始内容。
```

这个需求范围很小，便于快速看见结果。最后一句明确了数据保存方式，避免把刷新后恢复初始任务误认为程序出错。

### 第二步：查看生成结果

Agent 生成文件后，打开网页。页面内容可以类似下面的示意：

```text
我的待办事项

[ 输入任务名称                  ] [添加]

□ 检查支付回调                         [删除]
□ 核对订单状态                       [删除]
□ 检查库存同步                         [删除]

任务总数：3              已完成：0
```

将“检查支付回调”标记完成后，任务总数应仍为 3，已完成数量应变为 1。再添加一条“检查退款队列”，任务总数应变为 4。

这样就能直观看到：自然语言要求已经转变为可操作的功能。查看效果时，也要实际点击，确认功能正常。

### 第三步：继续提出修改

看到第一版后，追加一条要求：

```text
请增加“全部、未完成、已完成”三个筛选按钮。
切换按钮时，只显示对应任务。
底部的任务总数和已完成数量仍统计全部任务，不随筛选改变。
```

Agent 根据新要求修改文件。刷新查看修改后的页面时，按照第一版约定，任务会恢复到三条初始数据。重新把“检查支付回调”标记完成，再点击“已完成”，列表应该只显示这一条任务。

这就是一次典型的迭代：先做出基本版本，看到效果后，再增加明确的新功能。

### 第四步：出现问题时，给出具体反馈

假设标记完成后，已完成数量仍然显示 0，可以这样反馈：

```text
我打开页面，将“检查支付回调”标记为完成。
任务样式已经变化，但底部“已完成”仍显示 0，预期应该显示 1。
请检查计数更新逻辑，修正后重新验证。
```

这是用于讲解的假设故障。描述操作、实际结果和预期结果，比只说“做错了”更能帮助 Agent 找到问题。

### 从案例中理解工作循环

**说清需求 → 生成初版 → 打开查看 → 提出修改 → 检查结果。**

用户负责表达目标和判断效果，Agent 利用模型与工具完成具体工作。接下来学习不同软件时，这个基本过程仍然适用。

## 1.6 接下来学习什么

技术篇先介绍 WorkBuddy 的使用，再介绍 Codex 及 OpenAI、DeepSeek 两条模型路线，随后学习 MCP、Skills 的使用与制作，最后认识 DeepSeek Harness。项目实战篇将把这些能力用于企业已有系统的接入。

第一章先建立三个认识：Vibe Coding 让我们用自然语言参与应用开发；Agent 能借助工具连续推进任务；Skills 可以把反复使用的方法整理成可复用能力。

带着这些认识进入软件实操，就更容易理解：我们在向谁下达任务，软件正在调用什么能力，以及为什么仍然需要查看实际结果。
