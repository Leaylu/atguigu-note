# 电商 IT 值班交接：业务背景与处理口径

一家虚构电商公司有华东、华南、华北三家门店，IT 团队维护订单、支付、库存、履约和商品系统。准备交接时，需要从一周工单快照中找出需要接班人继续处理的事项。

数据基准统一为 **2026-10-12T12:00:00+08:00**。所有人员、系统事件、订单编号均为随机生成的教学虚构数据。不要使用电脑当前时间重新计算。快照不是完整事件日志，不能据此计算历史解决时长或故障损失。

## 文件字段

| 字段 | 含义 |
| --- | --- |
| ticket_id | 工单主键，需保持文本格式 |
| store / system | 门店与所属业务系统 |
| priority | P1、P2、P3、P4；数字越小越优先 |
| status | 待处理、处理中、已解决、已关闭 |
| created_at / updated_at | 带 +08:00 的创建与最近更新时间 |
| owner | 当前负责人；空值表示未指派 |
| order_id | 关联订单编号，可在第三章来源订单中查找；不能假设与交易异常必然一致 |
| summary | 用户报告的现象，不是已确认根因 |

## 清洗顺序

1. 全部字段完全一致的重复行只保留一行，并记录删除数量。
2. 同一 ticket_id 存在不同内容时，隔离该编号全部版本。不能按出现顺序或 updated_at 自动选一条。
3. 其余记录进入有效工单。owner 为空不删除，报告中显示“待指派”。
4. 待处理与处理中统称“未结工单”；已解决和已关闭不进入未结超时计算。
5. 统计数量时，一条工单只计一次。异常标签可能重叠，标签数量不可直接相加当成独立工单数。

## 超时规则

本例 SLA 指“未结工单从创建到基准时刻的最长允许等待时间”，不是首次响应时长。只在严格超过时计超时：

| 优先级 | 阈值（小时） |
| --- | ---: |
| P1 | 4 |
| P2 | 12 |
| P3 | 24 |
| P4 | 48 |

高优先级超时 = 未结、超时且优先级为 P1 或 P2。交接 Top20 按优先级升序、created_at 升序、ticket_id 升序排序取前20；完整清单另存，不能只统计展示的20条。

输出应包含输入盘点、清洗审计、有效工单、冲突记录、完整超时清单、Top20交接清单，以及真正可编辑的 Word 值班交接报告。所有结果写入 outputs，原始文件不修改。
