# 第 9 章：从工作经验中设计 Skill

本章从订单统计工作中提炼一个 Skill 的设计：先确定任务范围，再写清输入、输出、处理规则、异常分支和验收标准。

## 9.1 从一项重复工作中选题

### 先选具体任务

“做一个万能办公技能”很难设计，因为写故障处理单、统计订单和分析接口日志，输入、步骤和判断标准都不同。

可以从一个具体任务开始：

> 根据电商订单与反馈资料，生成口径一致的 Excel工作簿和 Word 订单巡检报告。

这个任务的输入比较明确，处理流程可以重复，结果也能回到原始记录中核对，适合整理成可复用的技能。

### 用四个问题判断是否值得制作

| 问题 | 本案例的回答 |
| --- | --- |
| 会不会重复做？ | 每天巡检都需要核对数据并整理异常 |
| 方法是否相对稳定？ | 去重、状态统计和报告结构可以固定 |
| 能不能获得必要输入？ | 需要订单记录，反馈可以选填 |
| 能不能判断结果好坏？ | 可以检查数量、公式、文件内容和事实依据 |

如果任务只做一次，直接提要求即可。如果业务口径还在争论，先明确口径；把不确定的方法写成技能，并不会让它自动变得可靠。

## 9.2 分清固定规则和每次变化的内容

### 固定的是方法，不是本次答案

本案例中可以固定的规则包括：

- 相同编号且字段完全相同的记录只统计一次。
- 同一编号内容不一致时隔离全部版本，保留冲突清单。
- 已支付口径包含已支付和已发货。
- 缺少来源渠道时保留记录，标为“未填写”。
- Excel 和 Word 使用同一套已核对的统计结果。

每次变化的内容包括巡检批次名称、订单记录、反馈、输出位置，以及用户明确提出的特殊要求。

本批可用订单7,930条、已支付口径6,352单只是指定输入的结果。技能保存计算方法，不固定输出数量。

### 口径变化要明确处理

如果下一次用户要求把待支付也计入某个指标，应将其命名为“未取消订单”等独立指标，并明确包含哪些状态。已支付口径仍包含已支付和已发货。不要悄悄改变原规则，再继续沿用旧标题。

第一版技能可以只支持本章约定的口径。遇到不同口径时说明差异，确认后再调整设计，比在一个技能里预设大量分支更容易维护。

## 9.3 把输入和输出写清楚

### 输入：什么必须有，什么可以没有

本案例的第一版输入限定为第三章约定的订单、支付、发货、商品和库存CSV及业务口径，避免一开始就同时处理扫描件、图片、各种表格和在线系统。

| 输入项 | 是否必需 | 缺少时如何处理 |
| --- | --- | --- |
| 订单记录及表头 | 必需 | 说明缺少资料，暂不生成正式统计 |
| 订单编号、门店、SKU、数量、状态、金额与时间 | 必需字段 | 按规则隔离非法记录，说明统计范围 |
| 来源渠道 | 可缺失 | 保留记录，填写“未填写” |
| 巡检批次名称 | 可缺失 | 使用中性标题“电商订单统计” |
| 客服反馈 | 可缺失 | 不编造反馈，报告说明未提供 |
| 输出目录 | 任务开始时确定 | 优先使用用户明确选择的工作空间 |

“可缺失”也需要规则。例如，没有反馈时可以生成订单统计，但不能自动补出“客户普遍认可商城体验”的评价。

### 输出：交付可以打开的文件

本案例设计两个主要成果：

| 文件 | 应包含什么 |
| --- | --- |
| 交易核对工作簿.xlsx | 原始数据、清洗明细、异常、门店/渠道汇总和趋势；公式可重算 |
| 电商交易核对报告.docx | 清洗审计、支付异常、履约风险、建议与限制 |

保留输入文件。目标名称已存在时，选择新的编号名称并报告路径，例如 `订单统计-02.xlsx`，不默认覆盖已有成果。

还要区分“能打开”和“符合要求”：工作簿可以打开，但统计全部写死，就没有满足公式要求；Word 中有表格截图，也不等于交付了可编辑表格。

## 9.4 设计一条完整但不过度复杂的流程

可以把第三章的操作整理为下面六步：

1. **读取资料。** 确认输入、输出目录与必要工具可用。
2. **检查数据。** 核对字段、重复编号、状态值和缺失内容。
3. **整理并计算。** 按规则去重和隔离，支付先聚合再关联，计算支付与履约指标。
4. **生成 Excel。** 写入原始记录、清洗明细、统计公式与图表，核对计算结果。
5. **编写 Word。** 使用已核对的数据组织简报，区分事实、反馈和建议。
6. **检查与交付。** 检查两份文件、核对数字一致性，报告位置和未完成事项。

这里最重要的顺序关系是：数据未确认，就不要先写一份看起来完整的正式简报。

### 给容易出错的地方补上判断

| 情况 | 设计中的处理方法 |
| --- | --- |
| 完全重复的记录 | 去重后计算，保留原始行和去重说明 |
| 同一编号的状态不同 | 隔离全部版本，保留差异，明确可用订单统计范围 |
| 出现未定义状态 | 列出记录和原值，不强行归入已支付 |
| 没有反馈 | 正常完成订单统计，简报说明反馈缺失 |
| 无订单记录但表结构完整 | 输出零值统计，说明暂无数据，不推断原因 |
| 无法生成或检查办公文件 | 说明缺少的工具与当前完成范围，不宣称已交付合格文件 |

不是每个问题都要停止全部工作。例如，缺少反馈不影响订单计数；但冲突必须隔离并说明，不能把清洗后统计冒充全部原始业务。

## 9.5 先写检查标准，再决定怎么实现

### 用现有样例确定正确答案

第三章[输入资料](资料/第03章/输入资料)及[业务口径](资料/第03章/输入资料/案例说明与口径.md)定义检查条件：

| 检查项 | 预期 |
| --- | ---: |
| 原始订单行数 | 8,150 |
| 完全重复行数 | 120 |
| 冲突编号数／冲突版本行数 | 30／60 |
| 非法订单／可用订单 | 40／7,930 |
| 已支付口径订单 | 6,352 |
| 支付异常订单 | 79 |
| 超时未发货／其中当前库存不足 | 2,335／905 |

Excel公式引用明细，图表引用汇总，Word与Excel数字一致。更换随机种子后重新计算，不能沿用固定答案。新样本可使用[生成与校验工具](资料/WorkBuddy业务数据工具/README.md)。

### 再考虑指令、模板和脚本

| 实现方式 | 适合放什么 |
| --- | --- |
| 技能说明 | 适用条件、执行顺序、异常处理和检查要求 |
| 参考资料 | 订单状态定义、字段说明、正确与错误示例 |
| 模板 | Word 简报结构、Excel 工作表布局 |
| Python 脚本 | 后续需要稳定复用的去重、计数或数据校验 |

第一版不必把所有资源都准备齐。本章先完成设计；后续先从更小的故障行动项技能学习文件格式，再为复杂流程加入模板与脚本。

第五章的 Python 程序批量读取 JSON，执行校验、去重与冲突隔离；第三章则是多张业务 CSV，还包括支付和发货记录。字段、状态范围和业务规则不同，不能把原程序直接放进技能就宣称已经适配。若后续复用，应明确格式转换、关联与规则调整发生在哪里。

### 设计说明怎样映射成文件

| 设计内容 | 实现位置 |
| --- | --- |
| 用途与触发条件 | SKILL.md 的 description |
| 步骤、异常分支、检查要求 | SKILL.md 正文 |
| 较长的业务规则 | references 中的资料 |
| 输出结构 | assets 中的模板 |
| 稳定重复的计算 | scripts 中的程序 |

先根据任务需要决定文件，再创建目录。一个简单提取技能可以只有 `SKILL.md`；需要实际计算时，再加入经过检查的程序。

## 9.6 案例：把想法整理成一页设计说明

打开本章配套的[技能设计说明](资料/第09章/订单巡检报告技能设计说明.md)，查看任务范围、输入、输出、步骤和检查标准。

如果希望让 Agent 协助整理，可以输入：

```text
请根据第三章订单巡检资料和本章设计说明，检查“订单巡检报告”技能设计。
重点看输入是否完整、去重和已支付订单口径是否明确、异常处理是否遗漏。
检查 Excel 与 Word 的输出要求是否能够核验。
先列出需要澄清的问题；已有资料能回答的，引用依据说明。
本次只修改设计说明，不创建或安装技能，不生成办公成果。
```

重点观察它有没有把本次的6,352单写成固定规则，有没有把 Python、文档工具或输入格式当作已经具备的条件。

本章完成的是可供实施的设计，不是已经可调用的技能。下一章将从更简单的故障行动项提取开始，手工编写第一个 `SKILL.md`，认识名称、描述、正文和示例怎样组织。
