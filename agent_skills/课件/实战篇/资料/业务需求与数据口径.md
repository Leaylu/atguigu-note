# 订单异常排查与处理助手：业务需求

## 工作场景

商城 IT 工程师每天收到运营提交的订单排查请求。公司的订单、库存和履约信息已有接口，工程师希望通过 Codex 统一调用这些能力，减少反复切换系统与手工拼接信息。

需求分为两个层次：只读排查生成报告；需要处理时启动工作流，经审批后生成工单。创建工单不代表已经补货、退款或发货。

## 输入

| 字段 | 固定案例值 | 解释 |
| --- | --- | --- |
| 身份范围 | 店铺 A | 由 API 身份限定，不能由模型随意扩大 |
| paid_on | 2026-10-10 | 上海时区的支付日期 |
| as_of | 2026-10-11T12:00:00+08:00 | 判断超时的明确基准 |
| 时限 | 24 小时 | 只计严格超过的记录 |
| request_id | order-demo-001 | 需要工单处理时提供的启动幂等键 |

支付日期采用当日 00:00（含）至次日 00:00（不含）。候选订单同时满足店铺权限、支付日期、当前状态 paid 和付款后等待超过 24 小时。

`as_of` 并不提供历史数据库回放。订单状态、库存与履约摘要是查询时的内容；实际业务如需历史状态，需要已有系统提供相应快照或事件查询能力。

## 固定案例结果

| 订单 | 事实 | 分析表达 | 建议 |
| --- | --- | --- | --- |
| A1001 | 08:00 支付；数量 2；当前库存 0 | 当前库存不足，可能影响发货 | 核实库存分配及补货计划 |
| A1002 | 09:00 支付；当前库存 20；warehouse_hold | 有仓库拦截记录，备注为地址核验未通过 | 联系履约人员核实拦截原因 |
| A1003 | 10:00 支付；当前库存 20；无履约摘要 | 证据不足，原因待确认 | 检查履约同步与仓库处理状态 |

A1004 只等待 18 小时，A1005 已发货，A1006 已取消，均不进入异常清单。B1001 不属于当前身份可访问范围。

## 报告要求

报告包含查询范围、基准时间、分页完整性、异常清单、证据、可能原因、建议和待确认事项。出现错误必须说明哪些部分未完成，不能把接口失败写成“没有异常”。

已有数据没有提供责任人、预计恢复时间、补货日期或发货承诺，报告不得补造这些信息。

## 工单处理要求

1. 用户提出处理需求后启动工作流，保存待审批报告。
2. 人工独立核对并提交 approve 或 reject。
3. Agent 只能读取已有审批决定后恢复流程。
4. 批准后只处理已审批清单，重查订单是否仍符合条件。
5. 已有工单返回 existing，状态已变化返回 skipped_changed；首次创建返回 created。
6. 同一请求重复提交不启动新流程；同一订单重复处理不创建第二张工单。

## 交付成果

- 一份可核对原始接口结果的 Markdown 报告。
- 一个明确的 workflow_id，以及审批与处理状态。
- 本次新建、已有和跳过的工单明细。
- 可交给 WorkBuddy 整理的业务 JSON 和 Markdown 文件，不包含任何令牌配置。
